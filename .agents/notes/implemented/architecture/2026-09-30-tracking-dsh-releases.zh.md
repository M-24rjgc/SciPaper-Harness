# Agent Note：通过真实合并跟进 DeepSeek Harness 版本

状态：已实现

[English](2026-09-30-tracking-dsh-releases.md) | 中文

## 问题

SciPaper Harness 起初是 DeepSeek Harness 0.1.6-alpha.1 的一份拷贝。[独立身份的决定](2026-09-24-scipaper-independent-identity.zh.md)停止了对上游版本的跟进，因为上游已经领先数千个提交，每次合并都像一次手工解决的重写。代价是产品得不到上游持续修复的成果：Windows 的 shell 与沙箱、模型目录、持久化迁移、新的客户端功能。产品也需要一种方式说明继承的代码对应上游哪个版本，而自己的版本线（`0.2.0-alpha.N`）对此没有任何说明。

## 决定

继承来的单仓库就是产品的内核，内核通过真实的 Git 合并跟进上游的发布标签。

- **接通历史。** 导入提交已与上游标签的历史相连，`git merge <标签>` 有真实的合并基点。合并先落在一个分支（`upgrade/dsh-<版本>`），不直接进入 `main`。
- **两条版本线。** 每个同步版本的 `package.json` 用 `version` 记录产品版本，用 `scipaper.kernel { name, version, revision }` 记录内嵌的上游版本。产品保持在 `0.2.0-alpha.N`：桌面端更新器按该后缀推导渠道，不会把 `-rc` 版本推给 alpha 安装，所以版本行冲突一律保留我方。`getDshRuntimeVersion()` 读取内核标记，插件兼容性检查以它为准。
- **盖章。** 每次合并后，把所有清单的内核块改写为被合并的标签及其完整提交。rc.2 的合并用一次脚本改写了 332 个清单。
- **生成文件重新生成，不做合并。** 插槽目录、持久化目录与 schema、格式索引、工具与配置目录、翻译哈希记录和第三方声明，在源码合并之后由各自的生成器重写。
- **产品改动保持可表达。** 研究版行为放在 `packages/research/*`、`packages/client/ui-research` 与 `packages/bundle/research-app` 中；对继承包的修改限于文案、配置和已记录的例外，每次合并都复查。

2026-09-30 的 rc.2 合并按此执行：

- 桌面 Host 现在有三个入口：`index`、`cli`（上游的终端命令）和 `office-cli`（我们的）。终端命令名为 `sph`，使用 SciPaper 的可执行文件名，并有自己的注册表键和互斥体。
- 研究预设把 `ask_user_question` 切换到上游的定时模式，默认超时为 `-1`。一次调用会一直等答案，这是检查点需要的；不阻塞的问题传入有限超时，agent 继续工作，答案之后作为用户消息送回。
- 通用设置里的 Session Log 上传开关，与其他遥测行一起在研究版中禁用。
- open-in-app 采用上游的目录路径属性，远程工作区的保护挪到两个插槽适配器里。
- 上游的会话格式仍是 V4；我们是 V5，因为它记录会话在哪里执行（SSH 工作区）。两条持久化记录链并存，将来上游若发布 V5，需要有意识地对齐。

## 后果

- 升级是一次合并，加脚本盖章、一遍生成器和验证阶梯，而不是移植。
- 我们编辑过的每个继承文件都可能在下次合并时冲突，所以新的产品工作先放在产品包里。
- 产品版本与内核版本不会再被混淆：`version` 是用户安装的，`scipaper.kernel.version` 是代码所基于的。

## 考虑过的替代方案

**继续手工移植修复。** 每个修复都很小，但数量没有上限，也没有任何记录说明代码对应上游哪个状态。

**采用上游的版本号。** 更新器将不再向现有 alpha 安装推送构建，产品也会看起来像上游的一个发布。

**每个标签都变基。** 会改写共享历史，每次变基重复同样的冲突；合并只需解决每个冲突一次。
