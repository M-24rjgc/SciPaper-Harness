# Agent Note: Knowledge graph sub-plugins and the evidence graph

Status: implemented

English | [中文](2026-10-01-knowledge-graph-sub-plugins.zh.md)

## Problem

The knowledge graph was one plugin, `research-knowledge-provider`, that a person could only switch on or off as a whole. The graph features that follow draw on different sources and cost different amounts: a domain map needs the graph engine and its corpus, while a view of what stands behind each conclusion needs only the project's own record. One switch could not offer the second without loading the engine, nor withdraw the first without losing recall and novelty checks. The Knowledge tab was a single explorer with no place for another view.

## Decision

**Five rows of one bundle.** The knowledge bundle inserts five rows, each with its own switch on the plugin page: `research-knowledge-provider` (`ctx.researchKnowledge`: recall, novelty and building, unchanged), `research-knowledge-map` (`ctx.researchKnowledgeMap`, which injects `researchKnowledge`), `research-knowledge-evidence` (`ctx.researchKnowledgeEvidence`, which injects nothing) `research-knowledge-memory` (`ctx.researchKnowledgeMemory`, which injects nothing) and `research-knowledge-relations` (`ctx.researchKnowledgeRelations`, which injects nothing). All five are subpath modules of the workbench package, and each exports its own `locale/*.json`, because the plugin page reads a row's name and description from the row's module, not from the bundle.

**A disabled plugin refuses by name.** `evidence-graph`, `memory`, `memory-carry`, `map-view`, `map-overlay` and the `relations-*` commands look their service up with `ctx.get` and throw an error that names the plugin and where to enable it. The map follows the engine because it injects it. `graph-status` reports `modules: { map, evidence, memory, relations }`, and the snapshot carries the same flags in `knowledge.modules`, so the Knowledge tab works with the engine off and shows only the views of plugins that are on. Disabling deletes nothing: the projections are computed, and the engine's files stay under `.research/kg`.

**One lifetime helper.** `OperationScope` holds the abort controller and the set of in-flight operations that `ResearchKnowledge.run` used to hold. The engine, the map and the relation graph run their work under one, so disabling any of them aborts the work with a reason naming the plugin and waits for it to settle.

**The evidence graph is a projection.** `buildEvidenceGraph` is a pure function of the project record and stores nothing. A claim's status comes from its recorded fields: a recorded contradiction stands; a claim that cites nothing is `proposed` when it is a hypothesis and `missing` otherwise; a claim that cites a source that is gone, stale or on another revision, or is recorded stale, is `stale`; a recorded proposal stays `proposed`; the rest are `supported`. The record does not tie a planned run to a claim, so the dashed placeholder for expected evidence is drawn only for a claim that cites nothing and that a run can test, from the runs in progress or finished without collected results, at most three. The sentences of the detail panel (where the claim is written, what supports it, what would invalidate it, the next step) are chosen in the client from this structure and the dictionary; nothing is generated by a model.

**The map reads one shipped layout.** `map-view` returns the positions of the built-in graph's papers from `runtime/kg/ai-map.bin` ([format](../../../../packages/research/workbench/runtime/kg/MAP-FORMAT.md)) as base64 bytes, with their regions and sparse areas, encoded once per loaded map; `map-papers` details the papers under the pointer. `map-overlay` places what the research holds over it: the idea is the agent's latest recall query, read from `.research/kg/recalls.json`, to which every recall in a project that is not an example appends, and otherwise the brief; an imported reference sits on its paper when the graph holds its title and is placed by a lexical recall otherwise, at most 80; then the papers of the last three recalls and the marks. The recall log is the only file the overlay depends on; it is derived, and a damaged log is replaced by the next recall.

**The memory is a projection of every record, and the person's switches decide what the agent reads.** `buildResearchMemory` is a pure function of the records of the researches that are not examples, not removed from the list and not the untouched draft, and stores nothing. Literature merges by the same title normalization the map uses, kept in `title-key.ts` so that neither plugin loads the other to compare titles. The record marks no baseline, so the finished experiments are listed by name with their command and metrics and none is called a baseline. The lessons are the facts the records hold: failed runs that recorded a reason or an exit code, and decisions other than the choice of mode; a record without such a fact shows no lesson. What a new research carries is a person's preference, `memoryCarry` in the research preferences, where a kind that is absent is on; `memory-carry` writes it and refuses the agent. The agent reads the carried kinds through `research_project memory`, from the researches other than its own, because that tool is mounted whether or not the engine is on, while `research_knowledge` is not. Nothing is copied into a new research: the agent sees the memory and decides, and the usual approval rules still apply to anything it imports or creates.

**The relation graph reads and writes only the project.** Its store is `.research/kg/relations.json`, its relations rest on quotations of the project's own sources or on completed runs, and the [relation graph note](../../proposed/feature/2026-10-01-knowledge-graph-relations.md) owns the data model, the grounding rule and the gap matrix's wording. The service wraps the pure backend in one `OperationScope`, so disabling the row aborts a reference-list fetch in flight; that fetch runs only as the person's job (`relations-citations`) and never from the agent. The caller sets the author of every proposal and correction: the desktop is the person, the agent's tool is the agent, and neither command input nor the tool schema carries an author. Entities, merges, re-checking quotations and fetching are the person's commands and refuse the agent in the operation, and an example research answers the reads and refuses the writes. The agent reads `relations-*` through `research_knowledge`, which is mounted only while the engine is on.

**The Knowledge tab.** A segmented control lists the views of the plugins that are on, opens on the evidence view when it is on, and opens on the catalog when a tool result searched for something. The evidence view places every card at a computed height in three fixed-height columns, so the lines between them are drawn from the layout without measuring the page, and it stacks the columns when the panel is narrower than 440 px.

## Alternatives considered

**One plugin with flags in its configuration.** A flag is not a switch on the plugin page, and a disabled feature would still load the engine and its corpus.

**Compute the statuses in the client from the snapshot.** The snapshot already carries claims, sources and runs, but the client would then own record semantics that `validateLinks` and `invalidate` define on the host, and the agent could not read the same graph.

**Write "what would invalidate it" with a model.** It costs tokens on every view, differs between reads, and says nothing the record's structure does not already say.

**Match a planned run to a claim by name or text.** The record holds no such relation, and a heuristic would draw a line the record does not support.

**Measure the cards in the browser to draw the lines.** It needs a resize observer and a second render pass, and cannot be tested in the jsdom lane. Fixed card heights need neither.

**Report the sub-plugin flags only in `graph-status`.** That command needs the engine, and the evidence view must work without it.

**Place the idea from the brief on every view.** A brief is often Chinese or broad and shares few words with the corpus; the agent's recall query is English and already ranked against the graph, so the overlay reuses it and falls back to the brief only before the first recall.

**Put the memory action on `research_knowledge`.** That tool is registered only while the engine is on, so switching the engine off would take the memory from the agent although the memory needs no engine.

**Call the finished experiments baselines.** A baseline is a role a run plays in a comparison, and the record holds no field for it; the name of a run is the author's word, not the record's.

**Copy the carried literature, environments and runs into a new research when it starts.** It would write records the agent and the person did not ask for, and a copied environment may not exist on this machine in the new folder.

**Keep a separate memory file.** It would go stale against the records it summarizes, and the switches are the only state that belongs to the memory itself.

## Consequences

The five switches are independent: the evidence view, the memory and the relation graph work on the records alone, the map can be withdrawn without losing recall, and the engine can be withdrawn while the evidence view and the memory stay. The bundle's plugin page lists five rows instead of one.

The research settings form builds its preferences from the fields it shows, so it re-attaches `memoryCarry` as it does `showExamples`; a form that forgot it would turn every switch back on. What the memory shows is only what the records hold: a person who never recorded a decision or a failure sees no lessons, and the Memory view says plainly when only one research has left memory.

The map plugin's row is on by default; it reads its 321 KB layout on the first map command, not at startup. A long claim or source name is clamped inside its fixed-height card; the full text is in the card's tooltip and the detail panel.

`ResearchSnapshot.knowledge` gained the required `modules` field, and the Knowledge tab's views are derived from it rather than from a command.

Pinned by the real-composition tests in `loader.spec.ts` that toggle each row and exercise the relation graph through the service, the projection tests in `knowledge-evidence.spec.ts` and `knowledge-memory.spec.ts`, and the client specs for the layout, the panel sentences and the Knowledge tab.
