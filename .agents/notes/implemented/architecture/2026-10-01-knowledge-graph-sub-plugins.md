# Agent Note: Knowledge graph sub-plugins and the evidence graph

Status: implemented

English | [中文](2026-10-01-knowledge-graph-sub-plugins.zh.md)

## Problem

The knowledge graph was one plugin, `research-knowledge-provider`, that a person could only switch on or off as a whole. The graph features that follow draw on different sources and cost different amounts: a domain map needs the graph engine and its corpus, while a view of what stands behind each conclusion needs only the project's own record. One switch could not offer the second without loading the engine, nor withdraw the first without losing recall and novelty checks. The Knowledge tab was a single explorer with no place for another view.

## Decision

**Three rows of one bundle.** The knowledge bundle inserts three rows, each with its own switch on the plugin page: `research-knowledge-provider` (`ctx.researchKnowledge`: recall, novelty and building, unchanged), `research-knowledge-map` (`ctx.researchKnowledgeMap`, which injects `researchKnowledge`) and `research-knowledge-evidence` (`ctx.researchKnowledgeEvidence`, which injects nothing). All three are subpath modules of the workbench package, and each exports its own `locale/*.json`, because the plugin page reads a row's name and description from the row's module, not from the bundle.

**A disabled plugin refuses by name.** `evidence-graph`, `map-view` and `map-overlay` look their service up with `ctx.get` and throw an error that names the plugin and where to enable it. The map follows the engine because it injects it. `graph-status` reports `modules: { map, evidence }`, and the snapshot carries the same flags in `knowledge.modules`, so the Knowledge tab works with the engine off and shows only the views of plugins that are on. Disabling deletes nothing: the projections are computed, and the engine's files stay under `.research/kg`.

**One lifetime helper.** `OperationScope` holds the abort controller and the set of in-flight operations that `ResearchKnowledge.run` used to hold. The engine and the map both run their work under one, so disabling either aborts the work with a reason naming the plugin and waits for it to settle.

**The evidence graph is a projection.** `buildEvidenceGraph` is a pure function of the project record and stores nothing. A claim's status comes from its recorded fields: a recorded contradiction stands; a claim that cites nothing is `proposed` when it is a hypothesis and `missing` otherwise; a claim that cites a source that is gone, stale or on another revision, or is recorded stale, is `stale`; a recorded proposal stays `proposed`; the rest are `supported`. The record does not tie a planned run to a claim, so the dashed placeholder for expected evidence is drawn only for a claim that cites nothing and that a run can test, from the runs in progress or finished without collected results, at most three. The sentences of the detail panel (where the claim is written, what supports it, what would invalidate it, the next step) are chosen in the client from this structure and the dictionary; nothing is generated by a model.

**The map is a shell.** `mapNotBuilt()` is the one function behind both map commands, and `MapViewPage` and `MapOverlayPage` are `{ built: false }` placeholders in `types.ts`. The map engine replaces the function and both types together; until then the map view says the map is not built.

**The Knowledge tab.** A segmented control lists the views of the plugins that are on, opens on the evidence view when it is on, and opens on the catalog when a tool result searched for something. The evidence view places every card at a computed height in three fixed-height columns, so the lines between them are drawn from the layout without measuring the page, and it stacks the columns when the panel is narrower than 440 px.

## Alternatives considered

**One plugin with flags in its configuration.** A flag is not a switch on the plugin page, and a disabled feature would still load the engine and its corpus.

**Compute the statuses in the client from the snapshot.** The snapshot already carries claims, sources and runs, but the client would then own record semantics that `validateLinks` and `invalidate` define on the host, and the agent could not read the same graph.

**Write "what would invalidate it" with a model.** It costs tokens on every view, differs between reads, and says nothing the record's structure does not already say.

**Match a planned run to a claim by name or text.** The record holds no such relation, and a heuristic would draw a line the record does not support.

**Measure the cards in the browser to draw the lines.** It needs a resize observer and a second render pass, and cannot be tested in the jsdom lane. Fixed card heights need neither.

**Report the sub-plugin flags only in `graph-status`.** That command needs the engine, and the evidence view must work without it.

## Consequences

The three switches are independent: the evidence view works on the project record alone, the map can be withdrawn without losing recall, and the engine can be withdrawn while the evidence view stays. The bundle's plugin page lists three rows instead of one.

The map plugin loads and answers that no map is built, so its row is on by default before it can do anything useful. A long claim or source name is clamped inside its fixed-height card; the full text is in the card's tooltip and the detail panel.

`ResearchSnapshot.knowledge` gained the required `modules` field, and the Knowledge tab's views are derived from it rather than from a command.

Pinned by the real-composition test in `loader.spec.ts` that toggles each row, the projection tests in `knowledge-evidence.spec.ts`, and the client specs for the layout, the panel sentences and the Knowledge tab.
